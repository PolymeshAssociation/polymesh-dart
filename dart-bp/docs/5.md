# Sender/Receiver Affirmations

## Affirmations
Once has settlement has been posted on chain, sender/receiver send their agreement along with a proof which proves that they are the party to that leg, and they have done a correct account state transition, invalidating previous state by submitting the nullifier and their revealing their new state. Note that they don't point to their old state in the accumulator.

For an account state to transition from $State_{old}$ to $State_{new}$,
- secret key $sk$, identity $id$ and asset-id $at$ should not change
- nullifier should be revealed as $\rho^i.G_5$
- nullifier secret key $\rho^i$ and randomness $s^i$ should change as: $\rho^{i+1} = \rho.\rho^i$, $s^{i+1} = s.s^i$

Old state
$$
State_{old} = sk.G_{Aff} + balance.G_1 + counter.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc} \quad State_{old} \in \mathbb{G}_p
$$

New state
$$
State_{new} = sk.G_{Aff} + balance'.G_1 + counter'.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc} \quad State_{new} \in \mathbb{G}_p
$$

$balance$ might or might not be same as $balance'$ depending on who is affirming or what kind of transaction it is. $counter'$ might be same or 1 more or 1 less than $counter$ depending on the kind of transaction.
Also, it must be proved that the $State_{old}$ has same asset-id $at$ that is in the leg and has the public key for the same secret key as in the account.


For a single leg settlement of amount $v$:

1. When a sender affirms a leg, its new account state's balance should be $v$ less than the old account's and its counter should increase by 1.
2. When a receiver affirms a leg, its new account state's balance should be same as the old account's and its counter should increase by 1.
3. Sender can revert its affirmation by creating a new account state which has the balance increased by $v$ and counter decreased by 1.
4. Receiver can revert its affirmation by creating a new account state with counter decreased by 1.
5. Once a settlement has been confirmed, i.e. it cant be reverted,
    - sender can send a counter update txn to decrease it's counter by 1
    - receiver can send a claim funds txn to increases it's balance by $v$ and decrease it's counter by 1.

However, sender and receiver do have an option to send an irreversible affirmation and in that case, they don't change their counter, unless the settlement expires in which case the party who had sent, reverses it. 

Table describing changes to balance and counter for various transactions. Subscripts $_s$ and $_r$ refer to txn sent by sender and receiver respectively.

| Transaction Type     | Description                                       | Balance Change | Counter Change |
| -------------------- | ------------------------------------------------- | -------------- | -------------- |
| **$Affirm_s$**       | Sender affirms a leg of amount $v$                | **-v**         | **+1**         |
| **$Affirm_r$**       | Receiver affirms a leg                            | **0**          | **+1**         |
| **$Claim_r$**        | Receiver claims funds after settlement            | **+v**         | **-1**         |
| **$CntUpd_s$**       | Sender updates counter after settlement           | **0**          | **-1**         |
| **$Reverse_s$**      | Sender reverses their affirmation                 | **+v**         | **-1**         |
| **$Reverse_r$**      | Receiver reverses their affirmation               | **0**          | **-1**         |
| **$Irr$-$Affirm_s$** | Sender irreversibly affirms a leg of amount $v$   | **-v**         | **0**          |
| **$Irr$-$Affirm_r$** | Receiver irreversibly affirms a leg of amount $v$ | **+v**         | **0**          |

### Leg configuration

A leg is created with two boolean configuration flags (see `LegEncConfig` and the "Leg" section in `4.md`):

- `reveal_asset_id`: if true, asset-id $at$ is revealed publicly to the verifier and there is no $CT_{at}$ ciphertext (the $r_4$ component of all ephemeral keys is also absent); if false, $at$ is encrypted as $CT_{at} = r_4.G_{Enc} + at.H$.
- `parties_see_each_other`: if true, the sender's ephemeral key carries an extra component for decrypting the receiver's encryption public key and vice versa. **This flag does not affect the affirmation proof** — each affirmer only ever uses their own ephemeral keys; the cross-keys only matter for decryption.

When an affirmation covers multiple legs of the same account (e.g. a swap settlement where the prover is sender of one leg and receiver of another), the asset-id might be revealed in some legs but not others. So per leg the affirmation proof distinguishes three sub-cases:

1. **Asset-id hidden** — no leg in this affirmation reveals $at$.
2. **Asset-id revealed in this leg** — $at$ is part of this leg's public data.
3. **Asset-id revealed elsewhere** — this leg has $CT_{at}$, but some other leg of the same affirmation reveals $at$, so $at$ is public to the verifier.

### Protocol

_The following description is for W1 (solo) where a single prover knows all witnesses including the secret keys $sk$ and $ek$. The split-prover variant used in W2/W3 is described after the Verifier section below._

This section describes a unified account state transition proof which can handle all the above scenarios and parts of this proof can be omitted when balance doesn't change.

Here the prover (sender/receiver) wants to prove following relations when sending affirmation for leg with amount $v$:

1. $State_{old} = sk.G_{Aff} + bal_0.G_1 + cnt_0.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc}$
2. Similarly, $State_{new} = sk.G_{Aff} + bal_1.G_1 + cnt_1.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}$
3. $State_{old}$ exists in the accumulator (account curve tree)
4. $N = \rho^i.G_5$
5. $\rho^{i+1} = \rho.\rho^i$
6. $s^{i+1} = s.s^i$
7. If balance change is expected,
    - $bal_1 = bal_0 - v$ (for **Affirm_s**, **$Irr$-$Affirm_s$**)
    - $bal_1 = bal_0 + v$ (for **Claim_r**, **Reverse_s**, **$Irr$-$Affirm_r$**)
8. Counter change:
    - $cnt_1 = cnt_0 + 1$ (**Affirm_s**, **Affirm_r**)
    - $cnt_1 = cnt_0 - 1$ (**Claim_r**, **CntUpd_s**, **Reverse_s**, **Reverse_r**)
    - $cnt_1 = cnt_0$ (**$Irr$-$Affirm_s$**, **$Irr$-$Affirm_r$**)
9. Since the change to counter is public, relation for $State_{new}$ can be expressed as:
    - $State_{new} - G_2 = sk.G_{Aff} + bal_1.G_1 + cnt.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}$ if counter increased by 1.
    - $State_{new} + G_2 = sk.G_{Aff} + bal_1.G_1 + cnt.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}$ if counter decreased by 1.
    - $State_{new} = sk.G_{Aff} + bal_1.G_1 + cnt.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}$ if counter remains same.
10. $bal_1 <= MAX\_BALANCE$ to avoid overflows
11. Prove that the party's account corresponds to the party in the leg. The account commitment contains $ek$ on $G_{Enc}$. The Bulletproof commitment includes both $ek$ and $ek^{-1}$ with the constraint $ek \cdot ek^{-1} = 1$, which allows $ek^{-1}$ to be used in ciphertext proofs. This binding consists of two parts — a participant proof that is **always** present, and an asset-id proof whose form depends on how the asset-id appears in this leg. (These correspond to the `AssetIdRevealed`, `AssetIdHidden`, and `AssetIdRevealedElsewhere` variants of `LegAccountLink`; all three carry the participant proof.)
    - **(11a) Participant ciphertext — always proved for every leg, regardless of the asset-id configuration.** Prove knowledge of $ek^{-1}$ and $ek$ in $CT_s = Eph_s \cdot ek^{-1} + G_{Enc} \cdot ek$ (sender) or $CT_r = Eph_r \cdot ek^{-1} + G_{Enc} \cdot ek$ (receiver), where $Eph_s$ ($Eph_r$) is the party's participant ephemeral key. $ek^{-1}$ comes from the Bulletproof commitment; $ek$ is shared from the account state commitment. This is the proof that ties the affirmer's account key to the party slot of the leg. It is the **only** such tie for transactions that neither change the balance nor have a hidden asset-id (e.g. $Affirm_r$, $CntUpd_s$, $Reverse_r$ on a leg whose asset-id is revealed in this leg), which is why it cannot be dropped in favour of the asset-id or amount proofs.
    - **(11b) Asset-id binding — additionally proved depending on how the asset-id appears in this leg:**
        - **Asset-id hidden**: additionally prove knowledge of $ek^{-1}$ and $at$ in $CT_{at} = Eph_{at} \cdot ek^{-1} + H \cdot at$, where $Eph_{at}$ is the party's ephemeral key for the asset-id ciphertext. $ek^{-1}$ comes from the Bulletproof commitment, $at$ is shared from the account state commitment proof. This binds the leg's encrypted asset-id to the account's asset-id.
        - **Asset-id revealed in this leg**: nothing additional — $at$ is public and is handled by subtracting $at \cdot G_3$ from the state targets (see steps 6–7).
        - **Asset-id revealed but not in this leg**: since $at$ is now public, additionally prove knowledge of $ek^{-1}$ in $CT_{at} - H \cdot at = Eph_{at} \cdot ek^{-1}$. $ek^{-1}$ comes from the Bulletproof commitment.
12. If transition involves a balance change, prove that amount in $CT_v$ is $v$: prove knowledge of $ek^{-1}$ and $v$ in $CT_v = Eph_v \cdot ek^{-1} + H \cdot v$, where $Eph_v$ is the party's ephemeral key for the amount ciphertext. $ek^{-1}$ comes from the Bulletproof commitment; $v$ is shared from the Bulletproof balance commitment.

**Instance**: $State_{old_r}$, $State_{new}$, $N$, $Path_r$, $Root$, $CT_s$, $CT_r$, $CT_v$, $CT_{at}$ (a ciphertext when asset-id is hidden, or the revealed value $at$ otherwise), $Eph_s$, $Eph_r$, $Eph_v$, $Eph_{at}$ (only when asset-id is hidden), $EK_s$, $EK_r$, $G_{Aff}$, $G_{Enc}$, $G_i$, $H$, $H_i$, $\widetilde{G}$, $\widetilde{G}_i$, $\widetilde{H}$, $\widetilde{H}_i$

Here $G_{Enc}$ is the generator for the $ek$ component of the account commitment, and also serves as the key generator in ciphertexts. $H$ is the generator for plaintext values in ciphertexts.

**Witness**: $sk, ek, id, v, bal_0, bal_1, cnt, \rho, \rho^i, \rho^{i+1}, s, s^i, s^{i+1}, Path$ and additionally $at$ when asset-id is hidden. $ek^{-1}$ is derived from $ek$ and committed in the Bulletproof with constraint $ek \cdot ek^{-1} = 1$.

Above are the high level instance and witness values known before the protocol starts and don't include instance and witness created during protocol execution like the various blindings and $T$ values.

#### Prover
1. Prover first wants to prove knowledge of $sk, ek, at, bal_0, cnt, \rho, \rho^i, s, s^i, id$ in the relation $$State_{old} = sk.G_{Aff} + bal_0.G_1 + cnt_0.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc}$$
2. Similarly, prover wants to prove knowledge of $sk, ek, at, bal_1, cnt, \rho, \rho^{i+1}, s, s^{i+1}, id$ in $State_{new}$ from relation 9.
    - If counter increased by 1: $$State_{new} - G_2 = sk.G_{Aff} + bal_1.G_1 + cnt_0.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}$$
    - If counter decreased by 1: $$State_{new} + G_2 = sk.G_{Aff} + bal_1.G_1 + cnt_0.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}$$
    - If counter remains same: $$State_{new} = sk.G_{Aff} + bal_1.G_1 + cnt_0.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}$$
3. Prover gets the path of the leaf $State_{old}$ as $Path$, an array of nodes (curve points), and randomizes it by adding blindings to all nodes. This will result in the leaf $State_{old}$ being transformed into $State_{old_r} = State_{old} + b_0.H_0$ and $Path$ transforms into $Path_r$. Prover enforces the constraints for curve tree membership using $Path, Path_r, b_i$.
4. Since prover knows the opening of $State_{old}$ and $b_0$, it can prove the knowledge of opening of $State_{old_r}$ as well. So relation 1 can be transformed as:
   $$
   sk.G_{Aff} + bal_0.G_1 + cnt_0.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc} + b_0.H_0 = State_{old_r}
   $$
5. Prover picks random $$sk_r, ek_r, at_r,  bal_{0_r},  cnt_r, \rho_r, \rho^i_r, \rho^{i+1}_r, s_r, s^i_r, s^{i+1}_r, id_r, b_{0_r} \in \mathbb{Z}_p$$ and creates:
   $$T_{State_{old_r}} = sk_r.G_{Aff} + ek_r.G_{Enc} +  bal_{0_r}.G_1 +  cnt_r.G_2 + at_r.G_3 + \rho_r.G_4 + $$
   $$\rho^i_r.G_5 + s_r.G_6 + s^i_r.G_7 + id_r.G_8 + b_{0_r}.H_0, \in \mathbb{G}_p$$
6. For the new state, create:
   $$T_{State_{new}} = sk_r.G_{Aff} + ek_r.G_{Enc} +  bal_{1_r}.G_1 +  cnt_r.G_2 + at_r.G_3 + \rho_r.G_4 + $$
   $$\rho^{i+1}_r.G_5 + s_r.G_6 + s^{i+1}_r.G_7 + id_r.G_8, \in \mathbb{G}_p$$

   Same blindings for $sk, ek, at, cnt, \rho, s, id$ are used in both old and new state since these values don't change. If balance doesn't change, also use same blinding so $bal_{0_r} = bal_{1_r}$.
7. For the correctness of nullifier, prover creates:
   $$
   T_{null} = \rho^i_r.G_5, \in \mathbb{G}_p
   $$
8. For enforcing $\rho^{i+1} = \rho.\rho^i$, $s^{i+1} = s.s^i$ and $ek \cdot ek^{-1} = 1$, prover sets up the constraints in Bulletproof. The first two are multiplications for randomness evolution, the third links $ek$ (committed in the account state) with $ek^{-1}$ (needed for ciphertext proofs). Prover uses Sigma protocol (Chaum Pedersen) to prove equality of committed values in Bulletproof's commitment and in the state commitments. Let $C_{BP_{\rho,s}}$ be the commitment:
     $$C_{BP_{\rho,s}} = b'.H_0 + \rho.H_1 + \rho^i.H_2 + \rho^{i+1}.H_3 + s.H_4 + s^i.H_5 + s^{i+1}.H_6 + ek.H_7 + ek^{-1}.H_8, \in \mathbb{G}_p$$
     _In W2/W3 the $ek \cdot ek^{-1} = 1$ constraint is not enforced via Bulletproofs; instead the device proves it via a Sigma protocol on a fresh element $D$, and $ek, ek^{-1}$ are dropped from $C_{BP_{\rho,s}}$. See the split prover variant below._
9. If the balance changes, prover sets up constraint in Bulletproof based on transaction type:
    - If balance change is $-v$: $bal_1 = bal_0 - v$
    - If balance change is $+v$: $bal_1 = bal_0 + v$

   Let $C_{BP_{bal}}$ be the commitment:
   $$
   C_{BP_{bal}} = b''.H_0 + v.H_1 + bal_0.H_2 + bal_1.H_3, \in \mathbb{G}_p
   $$
10. Prover creates commitment for $C_{BP_{\rho,s}}$ by picking random $r_{BP_{\rho,s}}, ek^{-1}_r \in \mathbb{Z}_p$:
    $$
    T_{BP_{\rho,s}} = r_{BP_{\rho,s}}.H_0 + \rho_r.H_1 + \rho^i_r.H_2 + \rho^{i+1}_r.H_3 + s_r.H_4 + s^i_r.H_5 + s^{i+1}_r.H_6 + ek_r.H_7 + ek^{-1}_r.H_8, \in \mathbb{G}_p
    $$
11. Prover creates commitment for $C_{BP_{bal}}$ by picking random $v_r, r_{BP_{bal}} \in \mathbb{Z}_p$:
    $$
    T_{BP_{bal}} = r_{BP_{bal}}.H_0 + v_r.H_1 +  bal_{0_r}.H_2 +  bal_{1_r}.H_3, \in \mathbb{G}_p
    $$
12. For the leg-account link, prover computes the $T$-values using only shared blindings — no new random value is picked.
    - **Participant (always)**: $T_{part} = ek^{-1}_r \cdot Eph_s + ek_r \cdot G_{Enc}$ (sender) or $T_{part} = ek^{-1}_r \cdot Eph_r + ek_r \cdot G_{Enc}$ (receiver), using $ek^{-1}_r$ from step 10 (Bulletproof commitment) and $ek_r$ shared with the account state commitment (step 5).
    - **Asset-id (additional)**, depending on the asset-id configuration:
        - **Asset-id hidden**: $T_{at} = ek^{-1}_r \cdot Eph_{at} + at_r \cdot H$, using $ek^{-1}_r$ from step 10 and $at_r$ from step 5.
        - **Asset-id revealed in this leg**: no asset-id $T$-value.
        - **Asset-id revealed but not in this leg**: $T_{at} = ek^{-1}_r \cdot Eph_{at}$, using $ek^{-1}_r$ from step 10 ($at$ is public, no blinding needed).
13. If balance changes, prover computes $T_v = ek^{-1}_r \cdot Eph_v + v_r \cdot H$, using $ek^{-1}_r$ from step 10 and $v_r$ from the Bulletproof balance commitment.
15. Prover hashes the following to create challenge $c$ as:
    $$c = Hash(State_{old_r}, State_{new}, N, Path_r, Root, txn\_type, CT_s, CT_r, CT_v, CT_{at}, Eph_s (\text{or } Eph_r), Eph_{at} (\text{or } at \text{ if revealed}), Eph_v, EK_s (\text{or } EK_r), C_{BP_{\rho,s}}, C_{BP_{bal}}, $$
    $$T_{State_{old_r}}, T_{State_{new}}, T_{null}, T_{BP_{\rho,s}}, T_{BP_{bal}}, T_{part}, T_{at}, T_v)$$
    ($T_{part}$ is present for every leg; $T_{at}$ only when the asset-id is not revealed in this leg; $T_v$ only when the balance changes.)
16. Prover creates responses for $resp_{state_{old_r}}$. When asset-id is hidden, $at$ is also a witness (11 elements). When revealed, $at$ is public and its generator $G_3$ is dropped (10 elements):
    - **Asset-id hidden**:
    $$[\begin{matrix}
    sk_r + sk.c, & ek_r + ek.c, & bal_{0_r} + bal_0.c, & cnt_r + cnt_0.c, & at_r + at.c, & \rho_r + \rho.c, & \rho^i_r + \rho^i.c, & s_r + s.c, & s^i_r + s^i.c, & id_r + id.c, & b_{0_r} + b_0.c\\
    \end{matrix}]$$
    - **Asset-id revealed** (no $at$ response; indices shift accordingly):
    $$[\begin{matrix}
    sk_r + sk.c, & ek_r + ek.c, & bal_{0_r} + bal_0.c, & cnt_r + cnt_0.c, & \rho_r + \rho.c, & \rho^i_r + \rho^i.c, & s_r + s.c, & s^i_r + s^i.c, & id_r + id.c, & b_{0_r} + b_0.c\\
    \end{matrix}]$$
17. Prover creates responses for $resp_{state_{new}}$. Most witnesses are shared ($\bot$). If balance changes, create response for $bal_1$. Using the same indexing as step 16:
    $$[\begin{matrix}
    \bot, & \bot, & bal_{1_r} + bal_1.c \text{ or } \bot, & \bot, & \bot, & \bot, & \rho^{i+1}_r + \rho^{i+1}.c, & \bot, & s^{i+1}_r + s^{i+1}.c, & \bot, & \bot\\
    \end{matrix}]$$
    (Indices match step 16: 0=$sk$, 1=$ek$, 2=$bal$, 3=$cnt$, 4=$at$ (hidden only), 5=$\rho$, 6=$\rho^i$, 7=$s$, 8=$s^i$, 9=$id$, 10=$b_0$)
18. Response for nullifier:
    $$resp_{null} = \rho^i_r + \rho^i.c$$
19. For relation $C_{BP_{\rho,s}}$, only the response for blinding $b'$ needs to be created:
    $resp_{b'} = r_{BP_{\rho,s}} + b'.c$
20. For relation $C_{BP_{bal}}$, only the response for blinding $b''$ and amount $v$ needs to be created:
    $resp_{b''} = r_{BP_{bal}} + b''.c$
    $resp_{v} = v_r + v.c$
21. No separate responses are created for $T_{part}$, $T_{at}$, or $T_v$ — all witnesses are shared:
    - $ek^{-1}$ response: reused from $resp_{BP_{\rho,s}}$ (the Bulletproof response at witness index 8). Used by the participant proof, the asset-id proof, and the amount proof.
    - $ek$ response (participant proof, always present): reused from $resp_{state_{old_r}}[1]$ (shared with account commitment).
    - $at$ response (asset-id hidden case): reused from $resp_{state_{old_r}}[4]$.
    - $v$ response: reused from $resp_v$ (balance Bulletproof response).
22. The proof is
    $$
    (C_{BP_{\rho,s}}, C_{BP_{bal}}, State_{old_r}, State_{new}, Path_r, N, T_{State_{old_r}}, T_{State_{new}}, $$
    $$T_{null}, T_{BP_{\rho,s}}, T_{BP_{bal}}, T_{part}, T_{at}, T_v, resp_{state_{old_r}}, resp_{state_{new}}, resp_{null}, $$
    $$resp_{b'}, resp_{b''}, resp_{v})
    $$


#### Verifier

1. Verifier knows the transaction type $txn\_type$ which determines counter direction and balance change expectations.
2. Verifier hashes the following to create challenge $c$ as:
   $$
   c = Hash(State_{old_r}, State_{new}, N, Path_r, Root, txn\_type, C_{BP_{\rho,s}}, C_{BP_{bal}}, $$
   $$T_{State_{old_r}}, T_{State_{new}}, T_{null}, T_{BP_{\rho,s}}, T_{BP_{bal}}, T_{part}, T_{at}, T_v)
   $$
3. Verifier enforces the Bulletproof constraints for the 2 multiplications: $\rho^{i+1} = \rho.\rho^i$ and $s^{i+1} = s.s^i$, and the inverse constraint $ek \cdot ek^{-1} = 1$.
4. Verifier enforces the Bulletproof constraint for the balance change based on $txn\_type$:
    - If $txn\_type \in \{Affirm_s, Irr-Affirm_s\}$: $bal_1 = bal_0 - v$
    - If $txn\_type \in \{Claim_r, Reverse_s, Irr-Affirm_r\}$: $bal_1 = bal_0 + v$
5. Verifier enforces the Bulletproof constraints for curve tree membership to verify that $Path_r$ leads to $Root$.
6. Verifies correctness of $State_{old_r}$. When asset-id is hidden, $G_3$ is part of the commitment and all 11 responses are used. When asset-id is revealed, $at \cdot G_3$ is subtracted from $State_{old_r}$ (since $at$ is public) and $G_3$ is dropped from the generator list, shifting indices 4+ down by one:
   - **Asset-id hidden** (indices 0–10 as in step 16 hidden case):
     $$resp_{state_{old_r}}[0].G_{Aff} + resp_{state_{old_r}}[1].G_{Enc} + resp_{state_{old_r}}[2].G_1 + resp_{state_{old_r}}[3].G_2 + resp_{state_{old_r}}[4].G_3 + $$
     $$resp_{state_{old_r}}[5].G_4 + resp_{state_{old_r}}[6].G_5 + resp_{state_{old_r}}[7].G_6 + resp_{state_{old_r}}[8].G_7 + $$
     $$resp_{state_{old_r}}[9].G_8 + resp_{state_{old_r}}[10].H_0 \stackrel{?}{=} T_{State_{old_r}} + State_{old_r}.c$$
   - **Asset-id revealed** (indices 0–9 as in step 16 revealed case; target adjusted by subtracting $at.G_3$):
     $$resp_{state_{old_r}}[0].G_{Aff} + resp_{state_{old_r}}[1].G_{Enc} + resp_{state_{old_r}}[2].G_1 + resp_{state_{old_r}}[3].G_2 + $$
     $$resp_{state_{old_r}}[4].G_4 + resp_{state_{old_r}}[5].G_5 + resp_{state_{old_r}}[6].G_6 + resp_{state_{old_r}}[7].G_7 + $$
     $$resp_{state_{old_r}}[8].G_8 + resp_{state_{old_r}}[9].H_0 \stackrel{?}{=} T_{State_{old_r}} + (State_{old_r} - at.G_3).c$$

7. Verifies correctness of $State_{new}$ by checking (reusing responses for shared witnesses from $resp_{state_{old_r}}$). The same hidden/revealed distinction applies as in step 6. Letting $D_{new}$ denote the adjusted $State_{new}$ (i.e., $State_{new}$ when hidden, or $State_{new} - at.G_3$ when revealed):
    - If counter increased by 1: target is $D_{new} - G_2$
    - If counter decreased by 1: target is $D_{new} + G_2$
    - If counter remains same: target is $D_{new}$

    The generator-to-response mapping follows step 16 (with $G_3$ and its response present or absent depending on whether asset-id is hidden or revealed). If balance doesn't change, $resp_{state_{new}}[2]$ is $\bot$ and verifier uses $resp_{state_{old_r}}[2]$ for both old and new balance responses. Similarly, $s$ (index 7) is shared between old and new states.

8. Verifies correctness of nullifier by checking:
   $$resp_{null}.G_5 \stackrel{?}{=} T_{null} + N.c$$
   $$\implies (\rho^i_r + \rho^i.c).G_5 \stackrel{?}{=} \rho^i_r.G_5 + N.c$$

9. Verifier checks response for $C_{BP_{\rho,s}}$ as:
   $$resp_{b'}.H_0 + resp_{state_{old_r}}[5].H_1 + resp_{state_{old_r}}[6].H_2 + resp_{state_{new}}[6].H_3 + resp_{state_{old_r}}[7].H_4 + $$
   $$resp_{state_{old_r}}[8].H_5 + resp_{state_{new}}[8].H_6 + resp_{state_{old_r}}[1].H_7 + resp_{BP_{\rho,s}}[8].H_8 \stackrel{?}{=} T_{BP_{\rho,s}} + C_{BP_{\rho,s}}.c$$
   $$\implies (r_{BP_{\rho,s}} + b'.c).H_0 + (\rho_r + \rho.c).H_1 + (\rho^i_r + \rho^i.c).H_2 + (\rho^{i+1}_r + \rho^{i+1}.c).H_3 + (s_r + s.c).H_4 + $$
   $$(s^i_r + s^i.c).H_5 + (s^{i+1}_r + s^{i+1}.c).H_6 + (ek_r + ek.c).H_7 + (ek^{-1}_r + ek^{-1}.c).H_8 \stackrel{?}{=} $$
   $$r_{BP_{\rho,s}}.H_0 + \rho_r.H_1 + \rho^i_r.H_2 + \rho^{i+1}_r.H_3 + s_r.H_4 + s^i_r.H_5 + s^{i+1}_r.H_6 + ek_r.H_7 + ek^{-1}_r.H_8 + C_{BP_{\rho,s}}.c$$
   Note: indices 5, 6 refer to $\rho, \rho^i$ responses from $resp_{state_{old_r}}$ (hidden asset-id case). When asset-id is revealed, these shift down by one (indices 4, 5).

10. Verifier checks response for $C_{BP_{bal}}$ as:
    $$resp_{b''}.H_0 + resp_v.H_1 + resp_{state_{old_r}}[1].H_2 + resp_{state_{new}}[1].H_3 \stackrel{?}{=} T_{BP_{bal}} + C_{BP_{bal}}.c$$
    $$\implies (r_{BP_{bal}} + b''.c).H_0 + (v_r + v.c).H_1 + ( bal_{0_r} + bal_0.c).H_2 + ( bal_{1_r} + bal_1.c).H_3 \stackrel{?}{=} r_{BP_{bal}}.H_0 + $$
    $$v_r.H_1 +  bal_{0_r}.H_2 +  bal_{1_r}.H_3 + C_{BP_{bal}}.c$$

11. Verifier checks the leg-account link using shared responses — no separate responses were created for $T_{part}$ or $T_{at}$.
    - **Participant (always checked)**, using $resp_{BP_{\rho,s}}[8]$ for $ek^{-1}$ and $resp_{state_{old_r}}[1]$ for $ek$:
      (sender) $$resp_{BP_{\rho,s}}[8] \cdot Eph_s + resp_{state_{old_r}}[1] \cdot G_{Enc} \stackrel{?}{=} T_{part} + CT_s \cdot c$$
      (receiver) $$resp_{BP_{\rho,s}}[8] \cdot Eph_r + resp_{state_{old_r}}[1] \cdot G_{Enc} \stackrel{?}{=} T_{part} + CT_r \cdot c$$
    - **Asset-id, additionally:**
        - **Asset-id hidden**: using $resp_{BP_{\rho,s}}[8]$ for $ek^{-1}$ and $resp_{state_{old_r}}[4]$ for $at$:
          $$resp_{BP_{\rho,s}}[8] \cdot Eph_{at} + resp_{state_{old_r}}[4] \cdot H \stackrel{?}{=} T_{at} + CT_{at} \cdot c$$
        - **Asset-id revealed in this leg**: no asset-id check ($at$ is public; steps 6–7 already subtract $at \cdot G_3$ from the state targets).
        - **Asset-id revealed but not in this leg**: using $resp_{BP_{\rho,s}}[8]$ for $ek^{-1}$; $at$ is public so the target is adjusted:
          $$resp_{BP_{\rho,s}}[8] \cdot Eph_{at} \stackrel{?}{=} T_{at} + (CT_{at} - H \cdot at) \cdot c$$

12. If balance changes, verifier checks the amount ciphertext using shared responses:
    $$resp_{BP_{\rho,s}}[8] \cdot Eph_v + resp_v \cdot H \stackrel{?}{=} T_v + CT_v \cdot c$$
    ($resp_{BP_{\rho,s}}[8]$ is the $ek^{-1}$ response from the Bulletproof commitment; $resp_v$ is the $v$ response from the Bulletproof balance commitment)

14. Verifier finally checks the Bulletproofs proof for all constraints i.e. curve tree membership, multiplications, inverse relation, and balance change

### Design notes — intentionally dropped optimizations

Two optimizations were deliberately omitted from the protocol above in favour of simpler, more uniform code. They are recorded here so a reader does not mistake them for oversights.

**Always proving the participant ciphertext.** The affirmation proves the participant relation ($CT_s$/$CT_r$) for every leg, even though it is not always strictly required. The leg-creation proof already establishes that a leg's amount and asset-id ephemeral keys ($Eph_v$, $Eph_{at}$) are formed from the same party public key as the participant ephemeral key ($Eph_s$/$Eph_r$). Consequently, whenever the affirmation already proves the asset-id relation (asset-id hidden or revealed elsewhere) or the amount relation (balance changes), the shared $ek^{-1}$ response together with the $ek \cdot ek^{-1} = 1$ constraint already binds the account key $ek$ to the leg's party slot, and the participant proof becomes redundant. It is *strictly* required only when neither of those is present — a transaction that neither changes the balance nor carries a hidden (or elsewhere-revealed) asset-id, such as a receiver affirmation, a counter update, or a reversal on a leg whose asset-id is revealed in that leg. An earlier version of this protocol exploited this: it proved the asset-id relation when it could and fell back to the participant relation only when necessary. That conditional structure was replaced by always proving the participant relation because the uniform version is much easier for non-cryptographers to read and maintain, at the cost of one redundant $\Sigma$-proof per leg in the cases where another ciphertext proof is already present. The redundancy argument relies on the leg's ephemeral keys being non-degenerate (e.g. $r_3, r_4 \ne 0$, so $Eph_v$, $Eph_{at}$ are not the identity), which can be guaranteed cheaply.

**Committing $ek$ rather than $ek^{-1}$ in the account state.** Twisted-ElGamal decryption and every per-leg ciphertext relation use $ek^{-1}$ (e.g. $CT - Eph \cdot ek^{-1}$). To make $ek^{-1}$ available as a witness bound to the account, the protocol commits $ek$ in the account state (as the public key $ek \cdot G_{Enc}$) and *additionally* commits $ek^{-1}$ in the Bulletproof, enforcing $ek \cdot ek^{-1} = 1$ with one multiplication; the $ek^{-1}$ response is then reused across the ciphertext relations. An earlier version instead committed $ek^{-1}$ directly in the account state, avoiding the extra committed value and the inverse constraint. That was safe: exposing $g^{ek^{-1}}$ alongside the public key $g^{ek}$ is the Inverse Decisional Diffie-Hellman problem (InvDDH), and Bao, Deng and Zhu (["Variations of the Diffie-Hellman Problem", 2003](https://ink.library.smu.edu.sg/cgi/viewcontent.cgi?params=/context/sis_research/article/2082/&path_info=Bao2003_VariationsOfDiffie_HellmanProblem_pv.pdf), §3.1–3.2) show $\text{InvDDH} \Leftarrow \text{SDDH} \Leftarrow \text{DDH}$ (SDDH = square DDH) — i.e. InvDDH is implied by the DDH assumption the scheme already needs for the semantic security of its Twisted-ElGamal ciphertexts, so it introduces no new assumption.

### Split prover variant (W2/W3)

In W2/W3 the work is split between a host (which does not know $sk, ek$) and a device (which holds $sk, ek$). Since $AK$ and $EK$ 
can't be revealed, the verifier reconstructs $State_{old_r}$ and $State_{new}$ from device partials and host partials that sum to them. The leg 
ciphertexts whose plaintexts are private (amount, and asset-id in the "hidden" sub-case) are also split between device and host with cancelling $\pm k$ blindings — the sum check enforces that device and host used the same $k$.

The $ek \cdot ek^{-1} = 1$ relation is no longer enforced via Bulletproof constraints. Instead the device proves it via a Sigma protocol on a fresh element $D$ (described below), and the $ek^{-1}$ response from that proof is the bridging element reused across all per-leg ciphertext checks on the device side.

#### Account commitment split

The device picks fresh independent randomness shares $r_{old,D}, r_{new,D} \in \mathbb{Z}_p$ and publishes:
$$P_{old,D} = sk.G_{Aff} + ek.G_{Enc} + r_{old,D}.H_0$$
$$P_{new,D} = sk.G_{Aff} + ek.G_{Enc} + r_{new,D}.H_0$$
The host's complementary partials are (asset-id hidden case shown; when asset-id is revealed, the $at.G_3$ term is omitted and added back as public by the verifier):
$$P_{old,H} = bal_0.G_1 + cnt_0.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + r_{old,H}.H_0$$
$$P_{new,H} = bal_1.G_1 + cnt_1.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + r_{new,H}.H_0$$
with $r_{old,D} + r_{old,H} = b_0$ (so old partials sum to $State_{old_r} = State_{old} + b_0.H_0$) and $r_{new,D} + r_{new,H} = 0$ (so new partials sum to $State_{new}$, which has no $H_0$ term). The host knows $r_{old,H}, r_{new,H}$; the device knows $r_{old,D}, r_{new,D}$. The two parties agree on these shares before proving — typically the device picks $r_{old,D}, r_{new,D}$ and the host derives its complementary values.

#### Device prover

1. **Account commitment partials.** Pick fresh blindings $sk_r, ek_r, r_{old,D_r}, r_{new,D_r} \in \mathbb{Z}_p$, reusing $sk_r, ek_r$ for both partials:
   $$T_{P_{old,D}} = sk_r.G_{Aff} + ek_r.G_{Enc} + r_{old,D_r}.H_0$$
   $$T_{P_{new,D}} = sk_r.G_{Aff} + ek_r.G_{Enc} + r_{new,D_r}.H_0$$
2. **D-relation** (replaces the $ek \cdot ek^{-1} = 1$ BP constraint). Pick fresh $r \in \mathbb{Z}_p$ and compute
   $$D = G_{Enc}.ek + H_0.r$$
   Since $G_{Enc} = D.ek^{-1} + H_0.(-r.ek^{-1})$, the device proves knowledge of $(ek^{-1}, -r.ek^{-1})$ in this relation. Pick blindings $(ek^{-1})_r, (-r.ek^{-1})_r$:
   $$T_D = D.(ek^{-1})_r + H_0.(-r.ek^{-1})_r$$
   The blinding $r$ hides $ek$ in $D$. This Sigma proof binds $ek^{-1}$ to the true inverse of $ek$ in $D$, and the $ek^{-1}$ response is reused as the bridging element in all per-leg ciphertext checks below.
3. **Per-leg participant proof** (always). For each leg, let $eph\_pk_{participant}$ be the party's ephemeral key for its role ($r_1$ for sender, $r_2$ for receiver). The relation
   $$ct_{participant} = eph\_pk_{participant}.ek^{-1} + G_{Enc}.ek$$
   is proven by reusing $(ek^{-1})_r$ from the D-relation and $ek_r$ from the account partials:
   $$T_{participant} = eph\_pk_{participant}.(ek^{-1})_r + G_{Enc}.ek_r$$
4. **Per-leg amount partial** (only when balance changes in this leg). Pick fresh $k_{amt} \in \mathbb{Z}_p$ and a blinding $k_{amt,r}$, publish
   $$P_{ct\_amount,D} = H_0.k_{amt} + eph\_pk_{amount}.ek^{-1}$$
   $$T_{P_{ct\_amount,D}} = H_0.k_{amt,r} + eph\_pk_{amount}.(ek^{-1})_r$$
5. **Per-leg asset-id:**
   - **Hidden**: pick fresh $k_{at} \in \mathbb{Z}_p$ and a blinding $k_{at,r}$, publish
     $$P_{ct\_at,D} = H_0.k_{at} + eph\_pk_{asset\_id}.ek^{-1}$$
     $$T_{P_{ct\_at,D}} = H_0.k_{at,r} + eph\_pk_{asset\_id}.(ek^{-1})_r$$
   - **Revealed elsewhere**: $at$ is public so no $k$ is needed. Prove discrete log of $(CT_{at} - at.H)$ over $eph\_pk_{asset\_id}$ with witness $ek^{-1}$ by reusing $(ek^{-1})_r$:
     $$T_{at,DL} = eph\_pk_{asset\_id}.(ek^{-1})_r$$
   - **Revealed in this leg**: nothing to prove for this leg's asset-id.
6. Device hashes its transcript — containing $nonce$, $P_{old,D}, P_{new,D}, D$, the per-leg partials $P_{ct\_amount,D}, P_{ct\_at,D}$, the leg encryptions, and all $T$ values above — to derive challenge $c$.
7. Device responses:
   - $s_{sk} = sk_r + sk.c$ (shared across both account partials)
   - $s_{ek} = ek_r + ek.c$ (shared across both account partials and per-leg participant)
   - $s_{r_{old,D}} = r_{old,D_r} + r_{old,D}.c$, $\quad s_{r_{new,D}} = r_{new,D_r} + r_{new,D}.c$
   - $s_{ek^{-1}} = (ek^{-1})_r + ek^{-1}.c$ (shared across D-relation, per-leg participant, per-leg amount, per-leg asset-id)
   - $s_{-r.ek^{-1}} = (-r.ek^{-1})_r + (-r.ek^{-1}).c$
   - Per leg with balance change: $s_{k_{amt}} = k_{amt,r} + k_{amt}.c$
   - Per leg with hidden asset-id: $s_{k_{at}} = k_{at,r} + k_{at}.c$

#### Device verifier

The verifier recomputes $c$ from the device's transcript and checks each Sigma relation. Each check has the standard structure $\text{(linear combination of responses)} \stackrel{?}{=} T + \text{(committed value)}.c$:
- $s_{sk}.G_{Aff} + s_{ek}.G_{Enc} + s_{r_{old,D}}.H_0 \stackrel{?}{=} T_{P_{old,D}} + P_{old,D}.c$
- $s_{sk}.G_{Aff} + s_{ek}.G_{Enc} + s_{r_{new,D}}.H_0 \stackrel{?}{=} T_{P_{new,D}} + P_{new,D}.c$
- $s_{ek^{-1}}.D + s_{-r.ek^{-1}}.H_0 \stackrel{?}{=} T_D + G_{Enc}.c$
- Per leg: $s_{ek^{-1}}.eph\_pk_{participant} + s_{ek}.G_{Enc} \stackrel{?}{=} T_{participant} + ct_{participant}.c$
- Per leg with balance change: $s_{ek^{-1}}.eph\_pk_{amount} + s_{k_{amt}}.H_0 \stackrel{?}{=} T_{P_{ct\_amount,D}} + P_{ct\_amount,D}.c$
- Per leg with hidden asset-id: $s_{ek^{-1}}.eph\_pk_{asset\_id} + s_{k_{at}}.H_0 \stackrel{?}{=} T_{P_{ct\_at,D}} + P_{ct\_at,D}.c$
- Per leg with asset-id revealed elsewhere: $s_{ek^{-1}}.eph\_pk_{asset\_id} \stackrel{?}{=} T_{at,DL} + (CT_{at} - at.H).c$

Reusing $s_{sk}, s_{ek}, s_{ek^{-1}}$ across multiple checks binds the same witnesses across them.

#### Host side (differences from W1)

The host runs the W1 prover above with the following changes:

- $sk, ek$ are dropped from the witness set. The $sk_r.G_{Aff} + ek_r.G_{Enc}$ terms are dropped from $T_{State_{old_r}}$ and $T_{State_{new}}$, and the corresponding responses are dropped.
- The host's targets are $P_{old,H}$ and $P_{new,H}$ in place of $State_{old_r}$ and $State_{new}$. The verifier reconstructs them as $State_{old_r} - P_{old,D}$ and $State_{new} - P_{new,D}$ (adding back $at.G_3$ as public when asset-id is revealed).
- $ek$ and $ek^{-1}$ are dropped from $C_{BP_{\rho,s}}$, along with the $ek \cdot ek^{-1} = 1$ Bulletproof constraint. The BP commitment now contains only $(\rho, \rho^i, \rho^{i+1}, s, s^i, s^{i+1})$ with the two multiplication constraints for randomness evolution.
- The leg-link terms ($T_{part}$, $T_{at}$, and $T_v$) and their shared responses are dropped from the host side — these live on the device. In their place:
  - For each leg with balance change, host publishes
    $$P_{ct\_amount,H} = H.amount + H_0.(-k_{amt})$$
    and proves knowledge of $(amount, -k_{amt})$ in it. The same $k_{amt}$ as the device's is used with the sign flipped — the device and host agree on this value before proving. The $amount$ response is shared with the balance BP's $v$ response.
  - For each leg with hidden asset-id, host publishes
    $$P_{ct\_at,H} = H.at + H_0.(-k_{at})$$
    and proves knowledge of $(at, -k_{at})$ in it. Same coordination of $k_{at}$ with the device. The $at$ response is shared with the host's account state Schnorr's $at$ response.
- The randomness shares $r_{old,H}, r_{new,H}$ get their own blindings in $T_{P_{old,H}}$ and $T_{P_{new,H}}$ (replacing the $b_0$ blinding in W1's $T_{State_{old_r}}$).

Nullifier, curve tree membership, randomness powers BP and its multiplication constraints, balance BP and its $bal_1 = bal_0 \pm v$ constraint, and the $bal_1 \leq MAX\_BALANCE$ range proof are all unchanged.

#### Verifier additions

In addition to running the device verifier and the host's state/nullifier/BP checks, the verifier:

- Reconstructs $State_{old_r} \stackrel{?}{=} P_{old,D} + P_{old,H}$ and $State_{new} \stackrel{?}{=} P_{new,D} + P_{new,H}$ (with $at.G_3$ added back to the host partials when asset-id is revealed).
- For each leg with balance change: $ct_{amount} \stackrel{?}{=} P_{ct\_amount,D} + P_{ct\_amount,H}$.
- For each leg with hidden asset-id: $CT_{at} \stackrel{?}{=} P_{ct\_at,D} + P_{ct\_at,H}$.

These sum checks implicitly enforce that the device and host used the same $k_{amt}$ (resp. $k_{at}$), since otherwise the $H_0$ contributions wouldn't cancel.

#### Binding host and device

**W2 (parallel).** The device's $nonce$ is the same $nonce$ the host uses, so both proofs end up bound to the same context. Device and host coordinate on the randomness shares ($r_{old,D}, r_{new,D}$ and per leg $k_{amt}, k_{at}$) before proving, since the verifier's sum checks require those values to line up; the two proofs are then produced and verified independently.

**W3 (sequential).** The host first runs its pre-challenge phase of the host prover above — picking all blindings and computing all host-side $T$ values, with $sk$- and $ek$-related parts dropped as described above. It then derives its challenge from that transcript exactly as the W1 challenge $c$ is derived but with the dropped $T$s omitted from the hash; call this challenge $c_H$. The host sends $c_H$ to the device. The device sets its $nonce$ to
$$nonce' = c_H \| nonce$$
(concatenation of the byte serialization of $c_H$ and the original $nonce$), runs the Device prover above against $nonce'$, and sends its full proof back to the host. The host appends the device proof bytes to its transcript and derives a fresh challenge
$$c_H' = Hash(c_H, \text{device proof bytes})$$
which it uses for its own response generation. The verifier mirrors the same ordering: derives $c_H$, reconstructs $nonce' = c_H \| nonce$, verifies the device proof against $nonce'$, then derives $c_H'$ from the device proof bytes and verifies the host's responses against $c_H'$.


## Proof of balance

An investor can be asked for proof of balance of certain account (of certain asset-id). 
The requester of this proof might be the auditor who has visibility of the pending settlements, or it 
might be someone else who the investor should prove that the sum of its finalized balance and balance 
in pending settlements is certain value. The prover's public key, asset-id and balance are revealed to the verifier. 
The investor also reveals the nullifier of the account to prove that it is using the latest account state as the verifier 
can check that nullifier has not been revealed. An improvement could be to prove knowledge of an unrevealed nullifier using a 
proof of non-membership in the nullifier set (nullifier set has to be an accumulator). 
The prover should share the index of account commitment in tree so verifier can efficiently fetch the commitment and compare. 
If its not possible then do a membership proof. Prover could hide the commitment by randomizing it with a new blinding ($State' = State + B.r'$)

There are 2 variants of this proof:

1. **Proof of balance with auditor**: The verifier is an auditor who already has visibility of the account state including the counter. The prover only needs to prove correctness of the public key and nullifier against the account commitment.
2. **Proof of balance with non-auditor**: The verifier is an arbitrary party who may not have visibility of pending transactions. The prover must prove the counter equals the number of legs provided, prove their role in each leg, and prove the sum of pending amounts.

### Proof of balance with auditor

In this protocol, the verifier is an auditor who already has access to the account commitment and knows the counter value. Both public keys $PK_{Aff}$ and $PK_{Enc}$ are revealed (the auditor knows the account). The prover must prove:

1. The secret key $sk$ in the account commitment corresponds to the revealed $PK_{Aff}$.
2. The encryption secret key $ek$ in the account commitment corresponds to the revealed $PK_{Enc}$.
3. The nullifier $N$ is correctly derived from $\rho^i$ in the account commitment.

**Instance**: $State, PK_{Aff}, PK_{Enc}, at, balance, counter, id, N, G_{Aff}, G_{Enc}$

**Witness**: $sk, ek, \rho, \rho^i, s, s^i$

#### Prover

1. Prover wants to prove knowledge of $\rho, \rho^i, s, s^i$ in the relation:
   $$\rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 = State - PK_{Aff} - PK_{Enc} - balance.G_1 - counter.G_2 - at.G_3 - id.G_8$$
   where the RHS is public.
2. Prover wants to prove knowledge of $\rho^i$ in $N = \rho^i.G_5$.
3. Prover wants to prove knowledge of $sk$ in $PK_{Aff} = sk.G_{Aff}$.
4. Prover wants to prove knowledge of $ek$ in $PK_{Enc} = ek.G_{Enc}$.
5. Prover picks random $\rho_r, \rho^i_r, s_r, s^i_r, sk_r, ek_r \in \mathbb{Z}_p$ and creates:
   $$T_{acc} = \rho_r.G_4 + \rho^i_r.G_5 + s_r.G_6 + s^i_r.G_7, \in \mathbb{G}_p$$
   $$T_{null} = \rho^i_r.G_5, \in \mathbb{G}_p$$
   $$T_{pk} = sk_r.G_{Aff}, \in \mathbb{G}_p$$
   $$T_{EK} = ek_r.G_{Enc}, \in \mathbb{G}_p$$
6. Prover hashes the following to create challenge $c$ as:
   $$c = Hash(State, PK_{Aff}, PK_{Enc}, at, balance, counter, id, N, T_{acc}, T_{null}, T_{pk}, T_{EK})$$
7. Prover creates responses:
   $$resp_{acc} = [\begin{matrix}
   \rho_r + \rho.c, & \rho^i_r + \rho^i.c, & s_r + s.c, & s^i_r + s^i.c\\
   \end{matrix}]$$
   $$resp_{pk} = sk_r + sk.c$$
   $$resp_{EK} = ek_r + ek.c$$
8. The proof is
   $$(N, T_{acc}, T_{null}, T_{pk}, T_{EK}, resp_{acc}, resp_{pk}, resp_{EK})$$

#### Verifier

1. Verifier hashes the following to create challenge $c$ as:
   $$c = Hash(State, PK_{Aff}, PK_{Enc}, at, balance, counter, id, N, T_{acc}, T_{null}, T_{pk}, T_{EK})$$
2. Verifies correctness of account state by checking:
   $$resp_{acc}[0].G_4 + resp_{acc}[1].G_5 + resp_{acc}[2].G_6 + resp_{acc}[3].G_7 \stackrel{?}{=} T_{acc} + (State - PK_{Aff} - PK_{Enc} - balance.G_1 - counter.G_2 - at.G_3 - id.G_8).c$$
   $$\implies (\rho_r + \rho.c).G_4 + (\rho^i_r + \rho^i.c).G_5 + (s_r + s.c).G_6 + (s^i_r + s^i.c).G_7 \stackrel{?}{=} \rho_r.G_4 + \rho^i_r.G_5 + s_r.G_6 + $$
   $$s^i_r.G_7 + (State - PK_{Aff} - PK_{Enc} - balance.G_1 - counter.G_2 - at.G_3 - id.G_8).c$$
3. Verifies correctness of nullifier by checking:
   $$resp_{acc}[1].G_5 \stackrel{?}{=} T_{null} + N.c$$
   $$\implies (\rho^i_r + \rho^i.c).G_5 \stackrel{?}{=} \rho^i_r.G_5 + N.c$$
4. Verifies knowledge of affirmation secret key by checking:
   $$resp_{pk}.G_{Aff} \stackrel{?}{=} T_{pk} + PK_{Aff}.c$$
   $$\implies (sk_r + sk.c).G_{Aff} \stackrel{?}{=} sk_r.G_{Aff} + PK_{Aff}.c$$
5. Verifies knowledge of encryption secret key by checking:
   $$resp_{EK}.G_{Enc} \stackrel{?}{=} T_{EK} + PK_{Enc}.c$$
   $$\implies (ek_r + ek.c).G_{Enc} \stackrel{?}{=} ek_r.G_{Enc} + PK_{Enc}.c$$

### Proof of balance with non-auditor

In this protocol, the verifier is an arbitrary party who may not have visibility of the pending transactions. The prover provides all pending leg encryptions and must prove:

1. The counter equals the number of legs provided.
2. The nullifier $N = \rho^i.G_5$ is correctly derived from the account commitment (so the verifier can check that the account state being referenced is the current, not-yet-invalidated one).
3. For each leg $k$, the prover has the correct role (sender or receiver). This is proven via the participant ciphertext: $ct_{participant,k} - PK_{Enc} = eph\_pk_{participant,k} \cdot ek^{-1}$, where $eph\_pk_{participant,k}$ is $r_1$ if the prover is the sender of leg $k$ and $r_2$ if the prover is the receiver. Only the holder of $ek$ can satisfy this relation with their own $PK_{Enc}$.
4. For each leg $k$, the asset-id matches the account's asset-id $at$:
    - If leg $k$ has $at$ revealed (`reveal_asset_id = true` for that leg), the verifier checks the revealed value directly against $at$ and no Sigma proof is needed.
    - If leg $k$ hides $at$, the prover proves $CT_{at_k} - at.H = eph\_pk_{at,k} \cdot ek^{-1}$, where $eph\_pk_{at,k}$ is the prover's ephemeral key for the asset-id ciphertext in that leg.
5. The sum of amounts in legs where prover is sender equals the declared pending sent amount. Let $S$ be the leg indices where prover is sender. The prover proves $\sum_{k \in S} CT_{v_k} - pending\_sent.H = (\sum_{k \in S} eph\_pk_{amount,s_k}) \cdot ek^{-1}$.
6. The sum of amounts in legs where prover is receiver equals the declared pending received amount. Let $R$ be the leg indices where prover is receiver. The prover proves $\sum_{k \in R} CT_{v_k} - pending\_recv.H = (\sum_{k \in R} eph\_pk_{amount,r_k}) \cdot ek^{-1}$.

**Instance**: $State, PK_{Aff}, PK_{Enc}, at, balance, counter, id, N, [Leg_k], pending\_sent, pending\_recv, G_{Aff}, G_{Enc}, H$

**Witness**: $sk, ek, ek^{-1}, \rho, \rho^i, s, s^i$

Here $Leg_k$ denotes the leg encryption for the $k$-th pending leg (including its ciphertexts and ephemeral keys). Both $PK_{Aff}$ and $PK_{Enc}$ are subtracted as public.

#### Prover

1. Prover wants to prove knowledge of $\rho, \rho^i, s, s^i$ in the account commitment relation:
   $$\rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 = State - PK_{Aff} - PK_{Enc} - balance.G_1 - counter.G_2 - at.G_3 - id.G_8$$
2. Prover wants to prove knowledge of $\rho^i$ in $N = \rho^i.G_5$ and $sk$ in $PK_{Aff} = sk.G_{Aff}$.
3. Prover proves knowledge of $ek$ in $PK_{Enc} = ek.G_{Enc}$ and of $ek^{-1}$ in $G_{Enc} = PK_{Enc}.ek^{-1}$. The second relation proves $ek^{-1}$ is the true inverse of $ek$ since $PK_{Enc}.ek^{-1} = G_{Enc}.ek.ek^{-1} = G_{Enc}$. The same blinding for $ek^{-1}$ is reused across all the ciphertext relations below.
4. For each leg $k$, prove knowledge of $ek^{-1}$ in the participant ciphertext:
   $$ct_{participant,k} - PK_{Enc} = ek^{-1} \cdot eph\_pk_{participant,k}$$
5. For each leg $k$ with hidden asset-id, prove knowledge of $ek^{-1}$ in the asset-id ciphertext:
   $$CT_{at_k} - at.H = ek^{-1} \cdot eph\_pk_{at,k}$$
6. If $S$ is not empty, prove knowledge of $ek^{-1}$ in the sum of sent amounts:
   $$\sum_{k \in S} CT_{v_k} - pending\_sent.H = ek^{-1} \cdot \sum_{k \in S} eph\_pk_{amount,s_k}$$
7. If $R$ is not empty, prove knowledge of $ek^{-1}$ in the sum of received amounts:
   $$\sum_{k \in R} CT_{v_k} - pending\_recv.H = ek^{-1} \cdot \sum_{k \in R} eph\_pk_{amount,r_k}$$
8. Prover picks random $\rho_r, \rho^i_r, s_r, s^i_r, sk_r, ek_r, ek^{-1}_r \in \mathbb{Z}_p$ and creates:
   $$T_{acc} = \rho_r.G_4 + \rho^i_r.G_5 + s_r.G_6 + s^i_r.G_7$$
   $$T_{null} = \rho^i_r.G_5$$
   $$T_{pk} = sk_r.G_{Aff}$$
   $$T_{EK} = ek_r.G_{Enc}$$
   $$T_{G_{Enc}} = ek^{-1}_r.PK_{Enc}$$
   For each leg $k$: $T_{participant_k} = ek^{-1}_r \cdot eph\_pk_{participant,k}$
   For each leg $k$ with hidden asset-id: $T_{at_k} = ek^{-1}_r \cdot eph\_pk_{at,k}$
   $$T_{sent} = ek^{-1}_r \cdot \sum_{k \in S} eph\_pk_{amount,s_k} \quad \text{(if } S \neq \emptyset\text{)}$$
   $$T_{recv} = ek^{-1}_r \cdot \sum_{k \in R} eph\_pk_{amount,r_k} \quad \text{(if } R \neq \emptyset\text{)}$$
9. Prover hashes the following to create challenge $c$ as:
   $$c = Hash(State, PK_{Aff}, PK_{Enc}, at, balance, counter, id, N, [Leg_k], pending\_sent, pending\_recv,$$
   $$T_{acc}, T_{null}, T_{pk}, T_{EK}, T_{G_{Enc}}, [T_{participant_k}], [T_{at_k}], T_{sent}, T_{recv})$$
10. Prover creates responses:
    $$resp_{acc} = [\begin{matrix}
    \rho_r + \rho.c, & \rho^i_r + \rho^i.c, & s_r + s.c, & s^i_r + s^i.c\\
    \end{matrix}]$$
    $$resp_{pk} = sk_r + sk.c$$
    $$resp_{EK} = ek_r + ek.c$$
    $$resp_{G_{Enc}} = ek^{-1}_r + ek^{-1}.c$$
    No additional responses are created for $T_{participant_k}, T_{at_k}, T_{sent}, T_{recv}$ — they all reuse $resp_{G_{Enc}}$ (the $ek^{-1}$ response) at verification time.
11. The proof is
    $$(N, T_{acc}, T_{null}, T_{pk}, T_{EK}, T_{G_{Enc}}, [T_{participant_k}], [T_{at_k}], T_{sent}, T_{recv}, resp_{acc}, resp_{pk}, resp_{EK}, resp_{G_{Enc}})$$

#### Verifier

1. Verifier reconstructs the challenge $c$ as
   $$c = Hash(State, PK_{Aff}, PK_{Enc}, at, balance, counter, id, N, [Leg_k], pending\_sent, pending\_recv,$$
   $$T_{acc}, T_{null}, T_{pk}, T_{EK}, T_{G_{Enc}}, [T_{participant_k}], [T_{at_k}], T_{sent}, T_{recv})$$
2. Verifier checks that $counter$ equals the number of legs provided, and that for any leg $k$ which reveals its asset-id, the revealed value equals $at$.
3. Verifies correctness of account state by checking:
   $$resp_{acc}[0].G_4 + resp_{acc}[1].G_5 + resp_{acc}[2].G_6 + resp_{acc}[3].G_7 \stackrel{?}{=}$$
   $$T_{acc} + (State - PK_{Aff} - PK_{Enc} - balance.G_1 - counter.G_2 - at.G_3 - id.G_8).c$$
   $$\implies (\rho_r + \rho.c).G_4 + (\rho^i_r + \rho^i.c).G_5 + (s_r + s.c).G_6 + (s^i_r + s^i.c).G_7 \stackrel{?}{=} \rho_r.G_4 + \rho^i_r.G_5 + s_r.G_6 + $$
   $$s^i_r.G_7 + (State - PK_{Aff} - PK_{Enc} - balance.G_1 - counter.G_2 - at.G_3 - id.G_8).c$$
4. Verifies correctness of nullifier by checking:
   $$resp_{acc}[1].G_5 \stackrel{?}{=} T_{null} + N.c$$
   $$\implies (\rho^i_r + \rho^i.c).G_5 \stackrel{?}{=} \rho^i_r.G_5 + N.c$$
   Note that verifier uses $resp_{acc}[1]$ for checking both the account commitment and nullifier, proving that the same $\rho^i$ is used in both relations.
5. Verifies knowledge of affirmation secret key by checking:
   $$resp_{pk}.G_{Aff} \stackrel{?}{=} T_{pk} + PK_{Aff}.c$$
6. Verifies knowledge of encryption secret key by checking:
   $$resp_{EK}.G_{Enc} \stackrel{?}{=} T_{EK} + PK_{Enc}.c$$
7. Verifies that $ek^{-1}$ is the inverse of $ek$ by checking:
   $$resp_{G_{Enc}}.PK_{Enc} \stackrel{?}{=} T_{G_{Enc}} + G_{Enc}.c$$
   $$\implies (ek^{-1}_r + ek^{-1}.c).PK_{Enc} \stackrel{?}{=} ek^{-1}_r.PK_{Enc} + G_{Enc}.c$$
   Since $PK_{Enc} = ek.G_{Enc}$, this proves $ek.ek^{-1} = 1$.
8. For each leg $k$, verifier checks the participant relation using $resp_{G_{Enc}}$:
   $$resp_{G_{Enc}} \cdot eph\_pk_{participant,k} \stackrel{?}{=} T_{participant_k} + (ct_{participant,k} - PK_{Enc}).c$$
9. For each leg $k$ with hidden asset-id, verifier checks asset-id correctness:
   $$resp_{G_{Enc}} \cdot eph\_pk_{at,k} \stackrel{?}{=} T_{at_k} + (CT_{at_k} - at.H).c$$
10. If $S$ is non-empty, verifier checks the total sent amount:
    $$resp_{G_{Enc}} \cdot (\sum_{k \in S} eph\_pk_{amount,s_k}) \stackrel{?}{=} T_{sent} + (\sum_{k \in S} CT_{v_k} - pending\_sent.H).c$$
11. If $R$ is non-empty, verifier checks the total received amount:
    $$resp_{G_{Enc}} \cdot (\sum_{k \in R} eph\_pk_{amount,r_k}) \stackrel{?}{=} T_{recv} + (\sum_{k \in R} CT_{v_k} - pending\_recv.H).c$$


## Transparent transfers

A transparent transfer moves an asset between an on-chain account and an off-chain "transparent" address. Unlike a settlement, it has no receiver affirm — only the 
account holder produces the proof. The asset-id $at$ and the transfer amount $v$ are both publicly revealed.

There are two variants:

- **Withdraw**: balance decreases by $v$. A range proof on the new balance is enforced to prevent underflow.
- **Deposit**: balance increases by $v$. No range proof is needed — the chain rejects deposits that would overflow $MAX\_BALANCE$ before the proof is accepted.

In both, $counter$, $sk$, $ek$, $id$, $\rho$, $s$ and $at$ are unchanged across the state transition; only $balance$, $\rho^i$ and $s^i$ change. The account's affirmation public key $AK = sk.G_{Aff}$ is encrypted for each auditor of the asset using twisted ElGamal so the asset's auditors can identify which account performed the transfer.

Old and new states:
$$
State_{old} = sk.G_{Aff} + balance.G_1 + counter.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc}
$$
$$
State_{new} = sk.G_{Aff} + balance'.G_1 + counter.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}
$$
with $balance' = balance - v$ for withdraw or $balance' = balance + v$ for deposit.

### Protocol

_The following description is for W1 (solo) where a single prover knows both secret keys $sk$ and $ek$. The split-prover variant used in W2/W3 is described after the Verifier section below._

This section describes a unified protocol that handles both withdraw and deposit. The only differences are the sign of $v$ in the old-state relation and the presence/absence of the new-balance range proof; these are flagged inline.

Here the prover wants to prove following relations:

1. $State_{old} = sk.G_{Aff} + bal_0.G_1 + cnt.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc}$. Substituting $bal_0 = bal_1 \pm v$ (where $-v$ is for withdraw and $+v$ is for deposit) and rearranging:
    - **Withdraw**: $State_{old} - v.G_1 = sk.G_{Aff} + bal_1.G_1 + cnt.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc}$
    - **Deposit**: $State_{old} + v.G_1 = sk.G_{Aff} + bal_1.G_1 + cnt.G_2 + at.G_3 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc}$
2. $State_{new} = sk.G_{Aff} + bal_1.G_1 + cnt.G_2 + at.G_3 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc}$
3. $State_{old}$ exists in the accumulator (account curve tree)
4. $N = \rho^i.G_5$
5. $\rho^{i+1} = \rho.\rho^i$
6. $s^{i+1} = s.s^i$
7. Withdraw only: $bal_1 \leq MAX\_BALANCE$
8. The encrypted public key for the asset's auditors is correctly formed: $encrypted = r.G_{Enc} + sk.G_{Aff}$ and for each auditor key $EK_i$, $eph\_pk_i = r.EK_i$. Knowledge of $(r, sk)$ in $encrypted$ and $r$ in each $eph\_pk_i$ is proven, with $sk$ shared with $State_{old}, State_{new}$ and the same $r$ shared across all $eph\_pk_i$.

**Instance**: $State_{old_r}, State_{new}, N, Path_r, Root, at, v, \text{direction}, [EK_i]_{i=1}^n, encrypted, [eph\_pk_i]_{i=1}^n, G_{Aff}, G_{Enc}, G_i, H_i, \widetilde{G}, \widetilde{G}_i, \widetilde{H}, \widetilde{H}_i$

**Witness**: $sk, ek, bal_0, bal_1, cnt, \rho, \rho^i, \rho^{i+1}, s, s^i, s^{i+1}, id, b_0, r, Path$

Above are the high level instance and witness values known before the protocol starts and don't include instance and witness created during protocol execution like the various blindings and $T$ values. The variable $r$ is the ephemeral randomness used in the auditor key encryption.

#### Prover

1. Prover gets the path of $State_{old}$ as $Path$, randomizes it (blinding $b_0.H_0$ on the leaf and similar blindings on the path nodes), giving $State_{old_r} = State_{old} + b_0.H_0$ and $Path_r$. Curve tree membership constraints are enforced over $Path, Path_r$.
2. Letting $D_{old}$ denote the public RHS for the old state (which depends on direction):
    - **Withdraw**: $D_{old} = State_{old_r} - v.G_1 - at.G_3$
    - **Deposit**: $D_{old} = State_{old_r} + v.G_1 - at.G_3$

    Prover wants to prove knowledge of $sk, bal_1, cnt, \rho, \rho^i, s, s^i, id, ek, b_0$ in
    $$sk.G_{Aff} + bal_1.G_1 + cnt.G_2 + \rho.G_4 + \rho^i.G_5 + s.G_6 + s^i.G_7 + id.G_8 + ek.G_{Enc} + b_0.H_0 = D_{old}$$
3. Letting $D_{new} = State_{new} - at.G_3$, prover wants to prove knowledge of $sk, bal_1, cnt, \rho, \rho^{i+1}, s, s^{i+1}, id, ek$ in
    $$sk.G_{Aff} + bal_1.G_1 + cnt.G_2 + \rho.G_4 + \rho^{i+1}.G_5 + s.G_6 + s^{i+1}.G_7 + id.G_8 + ek.G_{Enc} = D_{new}$$
4. Prover picks random $sk_r, ek_r, bal_{1_r}, cnt_r, \rho_r, \rho^i_r, \rho^{i+1}_r, s_r, s^i_r, s^{i+1}_r, id_r, b_{0_r} \in \mathbb{Z}_p$ and creates:
    $$T_{State_{old_r}} = sk_r.G_{Aff} + bal_{1_r}.G_1 + cnt_r.G_2 + \rho_r.G_4 + \rho^i_r.G_5 + s_r.G_6 + s^i_r.G_7 + id_r.G_8 + ek_r.G_{Enc} + b_{0_r}.H_0$$
    $$T_{State_{new}} = sk_r.G_{Aff} + bal_{1_r}.G_1 + cnt_r.G_2 + \rho_r.G_4 + \rho^{i+1}_r.G_5 + s_r.G_6 + s^{i+1}_r.G_7 + id_r.G_8 + ek_r.G_{Enc}$$
    The blindings for $sk, ek, bal_1, cnt, \rho, s, id$ are reused between old and new states since these witnesses are the same in both.
5. For the correctness of nullifier, prover creates:
    $$T_{null} = \rho^i_r.G_5$$
6. For enforcing $\rho^{i+1} = \rho.\rho^i$ and $s^{i+1} = s.s^i$, prover sets up the constraints in Bulletproof. Prover uses Sigma protocol to prove equality of committed values in Bulletproof's commitment and in $State_{old}, State_{new}$. The commitment depends on direction (the new balance is appended only when balance decreases, for the range proof):
    - **Withdraw**: $C_{BP} = b'.H_0 + \rho.H_1 + \rho^i.H_2 + \rho^{i+1}.H_3 + s.H_4 + s^i.H_5 + s^{i+1}.H_6 + bal_1.H_7$
    - **Deposit**: $C_{BP} = b'.H_0 + \rho.H_1 + \rho^i.H_2 + \rho^{i+1}.H_3 + s.H_4 + s^i.H_5 + s^{i+1}.H_6$

    For withdraw, an additional Bulletproof range constraint enforces $bal_1 \leq MAX\_BALANCE$ on the $bal_1$ slot.
7. Prover commits to $C_{BP}$. Pick random $r_{BP} \in \mathbb{Z}_p$ and create
    $$T_{C_{BP}} = r_{BP}.H_0 + \rho_r.H_1 + \rho^i_r.H_2 + \rho^{i+1}_r.H_3 + s_r.H_4 + s^i_r.H_5 + s^{i+1}_r.H_6 \,(+\, bal_{1_r}.H_7 \text{ for withdraw})$$
8. For the encrypted public key:
    $$encrypted = r.G_{Enc} + sk.G_{Aff}$$
    $$eph\_pk_i = r.EK_i \quad \text{for each } i = 1, ..., n$$
    Prover picks random $r_r \in \mathbb{Z}_p$ (reusing $sk_r$ from step 4) and creates:
    $$T_{encrypted} = r_r.G_{Enc} + sk_r.G_{Aff}$$
    $$T_{eph\_pk_i} = r_r.EK_i \quad \text{for each } i = 1, ..., n$$
9. Prover hashes the following to create challenge $c$ as:
    $$c = Hash(State_{old_r}, State_{new}, N, Path_r, Root, at, v, \text{direction}, [EK_i], encrypted, [eph\_pk_i], C_{BP},$$
    $$T_{State_{old_r}}, T_{State_{new}}, T_{null}, T_{C_{BP}}, T_{encrypted}, [T_{eph\_pk_i}])$$
10. Responses for $resp_{state_{old_r}}$:
    $$[\begin{matrix}
    sk_r + sk.c, & bal_{1_r} + bal_1.c, & cnt_r + cnt.c, & \rho_r + \rho.c, & \rho^i_r + \rho^i.c, & s_r + s.c, & s^i_r + s^i.c, & id_r + id.c, & ek_r + ek.c, & b_{0_r} + b_0.c\\
    \end{matrix}]$$
11. Responses for $resp_{state_{new}}$ (most witnesses are shared from $resp_{state_{old_r}}$, indicated by $\bot$). Using the same indexing as step 10 (0=$sk$, 1=$bal$, 2=$cnt$, 3=$\rho$, 4=$\rho^i$, 5=$s$, 6=$s^i$, 7=$id$, 8=$ek$):
    $$[\begin{matrix}
    \bot, & \bot, & \bot, & \bot, & \rho^{i+1}_r + \rho^{i+1}.c, & \bot, & s^{i+1}_r + s^{i+1}.c, & \bot, & \bot\\
    \end{matrix}]$$
12. For $C_{BP}$, only the blinding response is created (other witnesses are reused from $resp_{state_{old_r}}$ and $resp_{state_{new}}$):
    $$resp_{b'} = r_{BP} + b'.c$$
13. Response for $r$ (used in encrypted pubkey):
    $$resp_r = r_r + r.c$$
14. The proof is
    $$(C_{BP}, State_{old_r}, State_{new}, Path_r, N, encrypted, [eph\_pk_i],$$
    $$T_{State_{old_r}}, T_{State_{new}}, T_{null}, T_{C_{BP}}, T_{encrypted}, [T_{eph\_pk_i}],$$
    $$resp_{state_{old_r}}, resp_{state_{new}}, resp_{b'}, resp_r)$$

#### Verifier

1. Verifier hashes the following to create challenge $c$ as:
    $$c = Hash(State_{old_r}, State_{new}, N, Path_r, Root, at, v, \text{direction}, [EK_i], encrypted, [eph\_pk_i], C_{BP},$$
    $$T_{State_{old_r}}, T_{State_{new}}, T_{null}, T_{C_{BP}}, T_{encrypted}, [T_{eph\_pk_i}])$$
2. Verifier enforces the Bulletproof constraints for the 2 multiplications: $\rho^{i+1} = \rho.\rho^i$ and $s^{i+1} = s.s^i$. For withdraw, additionally enforce the range proof $bal_1 \leq MAX\_BALANCE$.
3. Verifier enforces the Bulletproof constraints for curve tree membership to verify that $Path_r$ leads to $Root$.
4. Let $D_{old}$ be as defined in Prover step 2 (direction-dependent). Verifies correctness of $State_{old_r}$ by checking:
    $$resp_{state_{old_r}}[0].G_{Aff} + resp_{state_{old_r}}[1].G_1 + resp_{state_{old_r}}[2].G_2 + resp_{state_{old_r}}[3].G_4 + resp_{state_{old_r}}[4].G_5 + $$
    $$resp_{state_{old_r}}[5].G_6 + resp_{state_{old_r}}[6].G_7 + resp_{state_{old_r}}[7].G_8 + resp_{state_{old_r}}[8].G_{Enc} + resp_{state_{old_r}}[9].H_0 \stackrel{?}{=} T_{State_{old_r}} + D_{old}.c$$
5. Verifies correctness of $State_{new}$ by checking (reusing responses from $resp_{state_{old_r}}$ for shared witnesses):
    $$resp_{state_{old_r}}[0].G_{Aff} + resp_{state_{old_r}}[1].G_1 + resp_{state_{old_r}}[2].G_2 + resp_{state_{old_r}}[3].G_4 + resp_{state_{new}}[4].G_5 + $$
    $$resp_{state_{old_r}}[5].G_6 + resp_{state_{new}}[6].G_7 + resp_{state_{old_r}}[7].G_8 + resp_{state_{old_r}}[8].G_{Enc} \stackrel{?}{=} T_{State_{new}} + (State_{new} - at.G_3).c$$
6. Verifies correctness of nullifier by checking:
    $$resp_{state_{old_r}}[4].G_5 \stackrel{?}{=} T_{null} + N.c$$
7. Verifies $C_{BP}$ (with the $bal_1$ slot included only for withdraw):
    $$resp_{b'}.H_0 + resp_{state_{old_r}}[3].H_1 + resp_{state_{old_r}}[4].H_2 + resp_{state_{new}}[4].H_3 + resp_{state_{old_r}}[5].H_4 +$$
    $$resp_{state_{old_r}}[6].H_5 + resp_{state_{new}}[6].H_6 \,(+\, resp_{state_{old_r}}[1].H_7 \text{ for withdraw}) \stackrel{?}{=} T_{C_{BP}} + C_{BP}.c$$
8. Verifies the encrypted public key:
    $$resp_r.G_{Enc} + resp_{state_{old_r}}[0].G_{Aff} \stackrel{?}{=} T_{encrypted} + encrypted.c$$
    (the $sk$ response is reused from $resp_{state_{old_r}}[0]$, binding $sk$ used in the account commitment to the $sk$ encrypted for auditors).
9. For each auditor key $EK_i$, verifies the ephemeral key relation:
    $$resp_r.EK_i \stackrel{?}{=} T_{eph\_pk_i} + eph\_pk_i.c$$
    The same $resp_r$ is reused across all $EK_i$, binding the same $r$ in $encrypted$ and in every $eph\_pk_i$.
10. Verifier finally checks the Bulletproofs proof for all constraints i.e. curve tree membership, multiplications, and (for withdraw) the balance range proof.

### Split prover variant (W2/W3)

In W2/W3 the work is split between a host (which does not know $sk, ek$) and a device (which holds $sk, ek$). Since $AK$ and $EK$ are hidden inside the account commitment, the verifier reconstructs $State_{old_r}$ and $State_{new}$ from device partials and host partials that sum to them (same structure as for affirmations). The encrypted-pubkey-for-auditors part is produced entirely on the device side since it requires $sk$; there are no leg ciphertexts to split.

#### Account commitment split

Identical to the affirmations split: the device picks fresh independent randomness shares $r_{old,D}, r_{new,D} \in \mathbb{Z}_p$ and publishes
$$P_{old,D} = sk.G_{Aff} + ek.G_{Enc} + r_{old,D}.H_0$$
$$P_{new,D} = sk.G_{Aff} + ek.G_{Enc} + r_{new,D}.H_0$$
The host's complementary partials carry everything else with $r_{old,D} + r_{old,H} = b_0$ and $r_{new,D} + r_{new,H} = 0$.

#### Device prover

1. **Account commitment partials.** Pick fresh blindings $sk_r, ek_r, r_{old,D_r}, r_{new,D_r} \in \mathbb{Z}_p$ (same $sk_r, ek_r$ for both partials):
    $$T_{P_{old,D}} = sk_r.G_{Aff} + ek_r.G_{Enc} + r_{old,D_r}.H_0$$
    $$T_{P_{new,D}} = sk_r.G_{Aff} + ek_r.G_{Enc} + r_{new,D_r}.H_0$$
2. **Encrypted public key for auditors.** Pick fresh $r \in \mathbb{Z}_p$ and compute
    $$encrypted = r.G_{Enc} + sk.G_{Aff}$$
    $$eph\_pk_i = r.EK_i \quad \text{for each } i = 1, ..., n$$
    Pick blinding $r_r \in \mathbb{Z}_p$ (reusing $sk_r$ from step 1) and create:
    $$T_{encrypted} = r_r.G_{Enc} + sk_r.G_{Aff}$$
    $$T_{eph\_pk_i} = r_r.EK_i$$
3. Device hashes its transcript (containing $nonce$, $P_{old,D}, P_{new,D}, encrypted, [eph\_pk_i]$, all $T$ values) to derive challenge $c$.
4. Device responses:
    - $s_{sk} = sk_r + sk.c$ (shared across both account partials and the encrypted-pubkey proof)
    - $s_{ek} = ek_r + ek.c$ (shared across both account partials)
    - $s_{r_{old,D}} = r_{old,D_r} + r_{old,D}.c$, $\quad s_{r_{new,D}} = r_{new,D_r} + r_{new,D}.c$
    - $s_r = r_r + r.c$ (shared across $T_{encrypted}$ and all $T_{eph\_pk_i}$)

#### Device verifier

1. Recompute $c$ from the device's transcript.
2. Verify the account partials:
    $$s_{sk}.G_{Aff} + s_{ek}.G_{Enc} + s_{r_{old,D}}.H_0 \stackrel{?}{=} T_{P_{old,D}} + P_{old,D}.c$$
    $$s_{sk}.G_{Aff} + s_{ek}.G_{Enc} + s_{r_{new,D}}.H_0 \stackrel{?}{=} T_{P_{new,D}} + P_{new,D}.c$$
3. Verify the encrypted public key:
    $$s_r.G_{Enc} + s_{sk}.G_{Aff} \stackrel{?}{=} T_{encrypted} + encrypted.c$$
4. For each auditor key $EK_i$, verify the ephemeral key:
    $$s_r.EK_i \stackrel{?}{=} T_{eph\_pk_i} + eph\_pk_i.c$$

Reusing $s_{sk}$ across the account partials and the encrypted-pubkey check binds the same $sk$ across them.

#### Host side (delta from W1)

The host runs the W1 prover with the following changes:

- $sk, ek$ are dropped from the witness set. The $sk_r.G_{Aff} + ek_r.G_{Enc}$ terms are dropped from $T_{State_{old_r}}$ and $T_{State_{new}}$, and the corresponding responses are dropped.
- The host's targets are $P_{old,H}$ and $P_{new,H}$ in place of $State_{old_r}$ and $State_{new}$ (the verifier reconstructs them as $State_{old_r} - P_{old,D}$ and $State_{new} - P_{new,D}$).
- The encrypted-pubkey part of the proof ($T_{encrypted}, [T_{eph\_pk_i}], resp_r$) is dropped — it lives entirely on the device.
- The randomness shares $r_{old,H}, r_{new,H}$ get their own blindings in $T_{P_{old,H}}$ and $T_{P_{new,H}}$ (replacing the $b_0$ blinding in W1's $T_{State_{old_r}}$).

Nullifier, curve tree membership, $C_{BP}$ and its multiplication constraints (and the range proof on $bal_1$ for withdraw) are all unchanged.

#### Verifier additions

In addition to running the device verifier and the host's state/nullifier/BP checks, the verifier:

- Reconstructs $State_{old_r} \stackrel{?}{=} P_{old,D} + P_{old,H}$ and $State_{new} \stackrel{?}{=} P_{new,D} + P_{new,H}$.

#### Binding host and device

**W2 (parallel).** The device's $nonce$ is the same $nonce$ the host uses, so both proofs end up bound to the same context. Device and host coordinate on the randomness shares ($r_{old,D}, r_{new,D}$) before proving; the two proofs are then produced and verified independently.

**W3 (sequential).** The host first runs its pre-challenge phase of the host prover above — picking all blindings and computing all host-side $T$ values, with $sk$- and $ek$-related parts dropped as described above. It then derives its challenge from that transcript exactly as the W1 challenge $c$ is derived but with the dropped $T$s omitted from the hash; call this challenge $c_H$. The host sends $c_H$ to the device. The device sets its $nonce$ to
$$nonce' = c_H \| nonce$$
(concatenation of the byte serialization of $c_H$ and the original $nonce$), runs the Device prover above against $nonce'$, and sends its full proof back to the host. The host appends the device proof bytes to its transcript and derives a fresh challenge
$$c_H' = Hash(c_H, \text{device proof bytes})$$
which it uses for its own response generation. The verifier mirrors the same ordering: derives $c_H$, reconstructs $nonce' = c_H \| nonce$, verifies the device proof against $nonce'$, then derives $c_H'$ from the device proof bytes and verifies the host's responses against $c_H'$.
